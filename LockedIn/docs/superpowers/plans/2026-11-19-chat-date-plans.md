# Date Plans in Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let either person suggest a time on a shared place, agree on it in chat, and optionally export the confirmed date.

**Architecture:** Keep one actionable plan in the existing conversation and append immutable events through the normal chat message writer. Use the same account and conversation locks as chat, then refresh via the existing broker and unread state. Planning is an independent flag from place search.

**Tech Stack:** Next.js, React, Fastify, PostgreSQL/Prisma, Vitest, Playwright, Temporal polyfill, and iCalendar.

**Spec:** [Date plans in chat](../specs/2026-11-19-chat-date-plans-design.md)

## Global Constraints

- **Plan a date** beside the message composer; **Find together**, **Browse on my own**, **See picks for both of you** when ready. Keep the privacy note in search.
- **Suggest a time**, **Send suggestion**, **Waiting for their reply**, **Confirm**, **Suggest another time**, **Decline**, **Date confirmed**, **Add to calendar**.
- One actionable date plan per conversation at a time; one proposed time per revision; no calendar connection, phone push, email, reservations, or post-date check-in.
- Two existing chat types; no new Discovery eligibility rules; normal chat and its safety controls remain available.
- Future, unambiguous IANA wall-clock time, up to 90 days ahead; optional one-hour calendar export only for a future confirmed date.
- No partner's starting area, calendar details, or plan payload in notifications. Roll out with an additive migration and `DATE_PLANS_ENABLED=false`.
- Paths are relative to the inner `LockedIn/` project. Integration commands use only the existing disposable localhost wrapper, never a cloud database.

## Review Focus

- Ambiguous/repeated and nonexistent/skipped times, including zones outside the proposer's local zone, never silently shift the meeting (Task 1).
- A retried old confirmation after cancellation must not resurrect the date or fan out a second alert (Task 2).
- A failed chat append (for example rate limiting) must not leave an invisible pending plan or change an existing revision (Task 2).
- Turning off place search preserves date actions on existing shared spots and confirmed plans in both chat surfaces (Tasks 2–3).
- A live counterproposal must not erase a message draft, move the transcript's reading position, or allow confirmation of the displaced revision (Task 3).

### Task 1: Normalize proposed times and produce safe calendar files

**Files:** Create `services/api/src/features/date-plans/date-plan-time.ts`, `date-plan-calendar.ts`, and `date-plan-time.spec.ts` in the same directory; modify `services/package.json` and its lockfile.

**Interfaces:** `type DatePlanTimeInput = { localTime: string; timeZone: string; startsAt: string }`; `validateDatePlanTime(input: DatePlanTimeInput, now: Date): { startsAt: Date; timeZone: string } | null`; `createDatePlanCalendar(plan: { id: string; venueName: string; startsAt: Date; confirmedAt: Date }): { filename: string; contents: string }`. Task 2 supplies the authorization and state guard, not this pure encoder.

- [ ] **Tests:** `it("validates the selected zone and matching UTC instant")`: expect New York `2026-11-21T19:00` at `2026-11-22T00:00:00.000Z` valid and the same input at `2026-11-21T19:00:00.000Z` invalid; reject invalid zone, negative-offset pseudo-zone, past/exact-now, and beyond 90 days. `it("rejects both DST gaps and overlaps")`: expect `null` for New York `2027-03-14T02:30` and `2027-11-07T01:30` with clocks set the preceding day. `it("exports one hour with an escaped venue and stable UID")`: expect `DTSTART:20261122T000000Z`, `DTEND:20261122T010000Z`, matching UID across repeated exports and a single VEVENT even for venue names with newlines, commas, and semicolons; verify UTF-8 line folding.
- [ ] **Red:** From `services`, `npm test -- api/src/features/date-plans/date-plan-time.spec.ts`; expect failure on missing modules.
- [ ] **Implement:** Pin `@js-temporal/polyfill@0.5.1`. Require a minute-resolution local string and an actual named zone; derive the instant via [Temporal's reject disambiguation](https://tc39.es/proposal-temporal/docs/zoneddatetime.html#from), compare it with the submitted UTC instant, and validate the server clock bounds. Generate [iCalendar](https://www.rfc-editor.org/rfc/rfc5545) with CRLF, escaped TEXT, UTF-8 folded lines, no attendees or private details, and UID derived from the plan ID. Use the stored confirmation time for DTSTAMP and reject raw field injection.

### Task 2: Persist, authorize, and deliver date-plan events

**Files:** Modify `services/api/prisma/schema.prisma`, `services/api/src/app.ts`, `services/api/src/features/messaging/{messaging-message.service,messaging.types,messaging.routes}.ts`, `services/api/src/features/discovery/discovery-connection.service.ts`, and `services/scripts/verify-discovery.mjs`. **Interfaces:** `datePlansEnabled(): boolean`; `registerDatePlanRoutes(server: FastifyInstance): void`; `getActiveDatePlan(tx, conversation: ChatConversation, actorId: string, now: Date): Promise<DatePlanView | null>`; `applyDatePlanAction(tx, conversation: ChatConversation, actorId: string, input: DatePlanAction, now: Date): Promise<ChatResult<DatePlanReply> & { notify?: string[] }>`. Use existing account-bound mutation headers and owner-enveloped JSON at `/api/messaging/conversations/:id/date-plans` (GET `{activePlan}`, POST `{activePlan, message}`) and GET `/date-plans/:planId/calendar` (owner-bound `{filename, contents}`). `DatePlanAction`: `{action:"propose", sourceMessageId, requestId, time:DatePlanTimeInput}`; `counter` uses `planId, revision, requestId, time`; `confirm | decline | withdraw | cancel` use `planId, revision, requestId`. `DatePlanView`: `{id, sourceMessageId, venueName, startsAt, timeZone, revision, state:"pending"|"confirmed"|"declined"|"withdrawn"|"canceled", proposer:"self"|"partner"}`. Optional `Message.datePlanEvent` carries the immutable snapshot minus relative `proposer`, plus `action`; internal fingerprints never serialize. Both chat metadata routes add optional `datePlansConversationId` separate from `dateSpotsConversationId`.
