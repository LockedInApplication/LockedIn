# Mutual Discovery Preferences Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Require a private, explicit fit in both directions before two people can see or contact each other through new Discovery.

**Architecture:** Store owner-only matching settings separately from published profiles. Apply equivalent eligibility rules in the existing database search paths and in locked contact actions; leave the existing order of eligible profiles and all established chat permissions unchanged. Add the setup and edit experience to existing Discovery screens with no global signup change.

**Tech Stack:** Fastify, Prisma/PostgreSQL, Next.js/React, Zod, Vitest, existing two-account browser harness. No new service or provider.

**Spec:** [Mutual matching for the first Discovery pilot](../specs/2026-11-20-mutual-discovery-preferences-design.md)

## Global Constraints

- No inferred choices, preselected open preferences, relaxed matches on an empty page, or automatic profile publication, resume, or promotion.
- Exact birthday, derived age, matching gender and the member's choices are not displayed to others in this release or written into analytics, logs, notification copy, public profile or safety evidence.
- Keep existing chats, plans, direct invitations, shared spaces, reports and safety controls intact. No backfill, operator data deletion, production flag change, deployment, pilot opening, or reporting redesign in this plan.
- Use one UTC date per operation; a February 29 birthday advances on March 1 in a non-leap year. One successful birthday correction per rolling 30 days; removal never consumes the allowance, but re-enrollment inside 30 days after removal does.

## Review Focus

- Removing and quickly recreating a setup must not bypass a used birthday correction; issued or expired counters must not store birthday history (Task 1).
- On February 28 of a non-leap year, SQL and pair checks must agree for a February 29 birth, including exact chosen age boundaries (Tasks 1 and 2).
- A stale card, photo URL or cursor after a preference change must not expose an ineligible profile (Task 2).
- A now-ineligible pending invite still supports decline, withdraw and report, while an already accepted chat stays writable (Tasks 2 and 3).
- A successful setup save must not publish a draft, resume a paused profile, bypass a metro or lock-in check, or leave stale UI controls after a quiet refresh (Task 3).
